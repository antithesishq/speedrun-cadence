Verdict: stands

# Adversarial review: child-cancel-ack-after-close

The finding: a parent workflow cancels its started children. A child closes as canceled (`ChildWorkflowExecutionCanceled`)
**before** the parent records `ExternalWorkflowExecutionCancelRequested` for that child. The Go client v1.4.0 has already
deleted the child's decision state machine, so it panics with `unknown decision DecisionType: ChildWorkflow`. Every later
decision task fails (`WORKFLOW_WORKER_UNHANDLED_FAILURE`), and the parent never closes.
Source: `scratchbook/rca/hunt-liveness.md` section C2. Evidence: f04f parent-26 history in
`scratchbook/logs/hunt-liveness/p26_exec.txt:75-104` (ev18 Canceled c0, ev22 CancelRequested c0, ev24 DecisionTaskFailed
"unknown decision ... parent-26/c0").

## Correction to the RCA's mechanism (does not change the verdict)

The RCA says step 2 failed, that is, recording the ack in the parent. The log says otherwise: **step 1** failed. At vtime
257.56, cadence2 logs `Failed to cancel external workflow execution`, target `parent-26/c0`,
`error: code:deadline-exceeded`, `logging-call-at: transfer_active_task_executor.go:610`
(`log_f04_9190701013436246952.ndjson`). That call site is the error branch of `requestCancelExternalExecutionWithRetry`
(src/cadence-v1.4.5/service/history/task/transfer_active_task_executor.go:603-633). The RequestCancel RPC to the child's
shard committed `WorkflowExecutionCancelRequested` on c0, but its response was lost to the timeout. The error is
transient, so the task returned an error and released the parent lock. c0 then ran its cancel and closed as canceled,
and the parent recorded ev18. The task retry re-sent RequestCancel. c0 was closed and canceled with the same request
ID, so the server answered Noop success (engine/engineimpl/request_cancel_workflow_execution.go:57-63; master is the
same at :57-63). The retry then recorded ev22 through `requestCancelExternalExecutionCompleted` (:1325-1366). That
function checks only that the parent is running and that the RequestCancelInfo exists, and does not check the child's
state. The result is the same either way: a legitimate server retry orders the ack after the child's close event.

## Check 1: harness intervention

- Our workflow code is minimal and correct. `ParentWorkflow` (antithesis/client/workflows.go:261-283) only calls
  `ExecuteChildWorkflow` and `Future.Get`, with default `ChildWorkflowOptions` (WaitForCancellation=false,
  ParentClosePolicy TERMINATE). It does not call `RequestCancelExternalWorkflow` or do anything else unusual. The
  cancel of the children is generated by the client library when the parent's context is cancelled.
- The driver's trigger is a plain `CancelWorkflow(wid, runID)` (antithesis/client/main.go:345). It was acknowledged at
  229.62 (`rpc client3 cancel wid=parent-26 -> ok "cancel_requested"`). That is the documented public API.
- Between the cancel and the panic, the harness does nothing to the workflow: no reset, no terminate, no signal. The
  history in p26_exec.txt shows only server- and client-generated events. The parent hangs because the worker fails
  every decision task deterministically. This happens on client1 at 295, 305 and 315, on client3 at 368, and on
  client2 at 482, so all three independent workers fail the same way. A restart or a sticky-cache problem would not
  produce that.
- **Not harness-caused.**

## Check 2: configuration and tuning

- antithesis/config-template/dynamicconfig.yaml:1-33 sets the cache (20, 30s TTL), task-list partitions, ack
  intervals, drain=0 and decisionHeartbeatTimeout. None of these touches cancel handling, transfer-task retry, or the
  RequestCancel idempotency path. A small cache only means more mutable-state reloads, and the ordering here does not
  depend on reloads.
- The trigger is an RPC timeout after the call committed on the target. The history-to-history RPC deadline and the
  transfer-task retry are server defaults in our setup. Production sees the same window under DB latency, on a history
  host restart between the child update and the parent ack (at-least-once transfer tasks), or on a shard move.
- `NonDeterministicWorkflowPolicy` is left at its default (block). That default is what turns the panic into a
  permanent stall. With FailWorkflow the parent would fail instead of hanging. That is still wrong, but it would
  surface.
- **Would it happen with defaults? Yes.**

## Check 3: faults beyond the guarantee

- The race does need a fault-like event. In the fault-free path, `processCancelExecution` holds the parent's workflow
  lock across both steps (transfer_active_task_executor.go:548-559, `defer release`). The child's close then has to
  wait for that lock before it can write `ChildWorkflowExecutionCanceled` into the parent, so the ack comes first.
  This is the strongest defense: the bug needs an RPC deadline-exceeded (or a host crash) between the two steps.
- Why the defense does not hold: an RPC timeout whose response is lost after the call committed, and a history host
  restart in the middle of a task, are ordinary production events. Transfer tasks are at-least-once by design. The
  events active here (network partition and clog, a paused postgres, throttling; `active_faults` in the log lines) are
  within guarantees.md Guarantee 4 ("history/matching kills, shard and task list movement, partitions"). Guarantee 4
  says workflow code is "completely oblivious to any failures and downtime ... of the Cadence service itself". By
  vtime 600 faults had stopped long before, and the parent still never progressed. The stall is permanent, not a
  transient fault effect.

## Check 4: checker and workflow code. Can the assertion fire on documented behavior?

- The assertion is "every started workflow closes once faults stop" (driver/main.go:646). parent-26's input is
  `k=3`, children are chain workflows with n=2, and the execution timeout is 7200 s. The parent was cancelled at 229,
  so a correct client would close it as canceled within seconds. It stays open with repeating DecisionTaskFailed
  events. Nothing documented allows a cancelled workflow to stay open while workers poll it.
- Could the server's event order be "illegal history", making this a server bug and not a client bug? Each event is
  individually legitimate. Neither the server nor the docs promise that the ack is ordered before the child's close
  event. The Go client's own test `Test_ChildWorkflowStateMachine_CancelSucceed`
  (go.uber.org/cadence@v1.4.0/internal/internal_decision_state_machine_test.go:340-382) covers only the
  ack-then-canceled order. The client handles the symmetric case: a *completion* event in CancellationDecisionSent goes
  to `CompletedAfterCancellationDecisionSent` (internal_decision_state_machine.go:385-394) and keeps the machine to
  await the cancel outcome. A *canceled* event moves to Completed (:415-422), and `moveState` deletes the machine
  (:313-323). The late ack then reaches `getDecision` (:691-697 region, the "unknown decision" panic) through
  `handleExternalWorkflowExecutionCancelRequested` (:901-913). A late `RequestCancelExternalWorkflowExecutionFailed`
  hits the same path (:915-929). The contract between server and client does not match. The cheapest fix is in the
  client. A server-side guard is possible: skip recording the ack when the child is no longer pending.
- **Not a checker artifact and not API misuse.**

## Check 5: reproduction across runs, versions and fix-verify

- The signature (parent open, cancel sent, no pending children) appears in all five hunts: v1.4.5 f04f 66, v1.4.5-b
  bba4 27, master 3e97 104, master-b c26b 59, and fix-verify 1a0d 2 (hunt-liveness.md:32). Parent stragglers are present
  in every `closes_*.json` under scratchbook/logs/hunt-liveness/. Client logs carry `unknown decision DecisionType:
  ChildWorkflow` in every run, per the RCA counts.
- It reproduces on server v1.4.5, on master, and on the fix-verify build, so it is independent of the three fixed
  server findings and of server version. All runs use the same Go client v1.4.0 (the only full version in GOMODCACHE).
  The RCA reports that upstream go client master still has the same `handleCanceledEvent` and
  `handleExternalWorkflowExecutionCancelRequested`. I did not re-verify this offline.

## Strongest defense, and why it fails

"The fault-free path holds the parent lock across both steps, so this needs an injected RPC timeout or a crash.
That is a fault artifact." It fails because a lost RPC response after commit, and a crash between two cross-shard
writes, are exactly the failures that at-least-once transfer tasks exist to tolerate. Cadence promises
fault-obliviousness for them, and the resulting wedge is permanent after faults end. Secondary defense: "the server
emitted an odd order, so blame the server." That changes which component to fix. It does not make the violation a
false positive.

## Severity (for Uber engineers)

Medium. This is a liveness problem with no data loss. Any workflow that cancels a started child, including a cancelled
parent with started children (a common pattern), can wedge permanently when the cancel RPC times out after commit or a
history host restarts mid-task. Recovery needs a manual reset or terminate. The fix belongs in the Go client:
`childWorkflowDecisionStateMachine.handleCanceledEvent` from CancellationDecisionSent should keep the machine until the
cancel outcome arrives, or the ack and failure handlers should ignore an already-closed child. An optional server
guard would skip the ack when there is no pending child for the initiated ID.
